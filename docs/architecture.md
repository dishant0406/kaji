# Architecture

Kaji is a macOS-only SwiftUI app. It embeds official upstream libghostty through `GhosttyKit.xcframework` and keeps all app behavior inside the `Kaji/` executable target.

## Repo Shape

```text
Kaji/                       App target
KajiHookClient/             Native provider hook helper
KajiAgentRuntime/           TypeScript native Kaji Agent runtime
KajiParentAgentRuntime/      TypeScript Parent Agent runtime using Pi packages
GhosttyKit/                  C module exposing ghostty.h
GhosttyKit.xcframework/      Built libghostty artifact from ghostty-org/ghostty
Tests/KajiTests/            Swift Testing suite
docs/                        Project docs
scripts/                     Setup, checks, packaging
```

There is no iOS companion target, no shared protocol package, and no remote server layer.
`Kaji/Resources/HugeIcons/` carries the bundled Hugeicons free stroke-rounded font and CSS map used by the app icon wrapper.

## Core Runtime

- `Kaji/KajiApp.swift` wires the app scene graph, stores, in-app settings modal flow, and app delegate lifecycle.
- `KajiHookClient/` is a native Swift executable bundled beside the app binary. Provider hooks call it directly, and it posts normalized provider events to Kaji through macOS `DistributedNotificationCenter`.
- `Kaji/Services/AppEnvironment.swift` builds the concrete dependencies used by the app state.
- `Kaji/Models/AppState.swift` owns project selection, worktree selection, workspace tabs, split trees, and workspace persistence. Project selection is separate from workspace creation, so a selected project can render an empty state until the first tab is opened.
- `Kaji/Models/WorkspaceReducer.swift` is the state transition layer for workspace tabs, panes, splits, and focus.
- `Kaji/Services/GhosttyService.swift` owns the single `ghostty_app_t` instance and global Ghostty callbacks.
- `Kaji/Views/Terminal/GhosttyTerminalNSView.swift` is the AppKit bridge that creates and drives each `ghostty_surface_t`, including focus and occlusion updates so hidden panes can stay mounted without continuing to render at full cost.
- `Kaji/Views/Terminal/TerminalViewRegistry.swift` keeps terminal views alive across SwiftUI updates.

## Workspace Model

```text
Project -> Worktree -> WorktreeWorkspace -> WorkspaceTab -> SplitNode -> TabArea -> TerminalTab
```

- A `Project` is a top-level folder the user adds to Kaji.
- A `Worktree` is either the primary project checkout or a git worktree discovered or created for that project.
- `WorktreeWorkspace` owns the ordered top-level tabs for a worktree and remembers which workspace tab is active.
- `WorkspaceTab` is the user-facing tab in the title bar. It owns one full-canvas split tree plus the focused pane inside that tree.
- `SplitNode` stores the pane tree inside one workspace tab.
- `TabArea` remains the leaf model used by the split tree, but after the tab rewrite it acts as a pane container for one active content stack rather than as the app's primary tab concept. Inactive terminal, browser, and parent-agent panes stay mounted for live session continuity. Each pane owns one stable Monaco host for all editor tabs in that pane; switching files rebinds the existing web view to the next editor state and swaps Monaco models instead of rebuilding WebKit. Older clean editor backing stores can still be released by budget policy, while preview, diff, VCS, problems, and graph panes unmount their SwiftUI/AppKit content when inactive.
- `TerminalTab` is the content model hosted by a leaf pane and can represent a terminal, editor, VCS view, or diff viewer.
- `TabDragCoordinator` now serves pane-level arrangement only. Title-bar tabs are workspace tabs, not pane-local tabs.

Workspace state is persisted per worktree so every project can keep separate workspace tabs, split layouts, focus state, terminal sessions, editor tabs, and VCS layouts across launches. A project can also remain selected with no workspace root when its tabs are closed or before any tab has been opened.

## Major Subsystems

- Terminal: `GhosttyTerminalNSView`, `TerminalPane`, `TerminalSearchBar`, `TerminalSettingsStore`, and `GhosttyRuntimeEventAdapter`. `TerminalPane` keeps terminal views mounted for session continuity while propagating SwiftUI visibility into Ghostty occlusion state, and the embedded bridge starts the user's shell explicitly so Ghostty can detect shell integration before forwarding immediate scroll input with libghostty precision and momentum metadata. `GhosttyTerminalConfigDefaults` writes Kaji-managed terminal behavior keys such as shell integration, scroll speed, scrollback, clipboard, link, image-memory, quick-terminal sizing, and optional macOS 26 glass background opacity/blur into the generated Ghostty config. `GhosttyPerf` adds unified-log signposts around `ghostty_app_tick()` and emits runtime events for wakeup coalescing so Instruments and `./script/build_and_run.sh --telemetry` can inspect the hot path.
- Editor: `EditorTabState`, `MonacoEditorView`, `MonacoPreloadService`, `MonacoAssetServer`, `TextBackingStore`, and the bundled Monaco runtime under `Kaji/Resources/MonacoEditor`. The file editor is Monaco running inside a hardened `WKWebView` loaded from a loopback-only static asset server that serves only bundled Monaco files. Monaco uses a shared WebKit configuration, a non-persistent data store, a preloaded warm web view for the first pane editor host, and one reusable editor host per `TabArea` so first open and file tab switching avoid unnecessary white reload flashes. Monaco keeps per-model view state inside the runtime, rebinds bridge messages when the pane host moves between editor tabs, and owns editor language behavior, including highlighting, folding, quick outline, and marker production. `TextBackingStore` remains the Swift-side mirror with cached full-text and UTF-16 length metadata so save, search state, markdown preview sync, inline edits, line navigation, and agent tools can use synchronous Swift models. Monaco sends diagnostics back through the bridge to `DiagnosticsStore`; Kaji no longer runs editor language servers or Swift-native syntax, Tree-sitter, folding, symbol, viewport, or language-pack infrastructure for the file editor. KajiKit script editing uses SwiftUI text controls rather than the removed native editor stack.
- Git and VCS: `GitRepositoryService`, `GitWorktreeService`, `VCSTabState`, and the attached source-control panel under `Kaji/Views/VCS/`. Diff loading keeps git semantics in `GitRepositoryService`, parses patches directly into flat `DiffDisplayRow` values with optional inline change segments, and renders diff content through viewport-bounded AppKit drawing so large hunks avoid full-file `NSTextView` layout work while preserving the SwiftUI file headers, gutters, comments, split/unified modes, and context expansion controls.
- Projects and worktrees: `ProjectStore`, `WorktreeStore`, `ProjectOpenService`, and `WorktreeSetupRunner`.
- Workspace navigation: `FileSearchService`, `PaletteOverlay`, `QuickOpenOverlay`, `AskOverlay`, `WorktreeSwitcherOverlay`, `ExternalIDECatalog`, `ExternalIDESettings`, and `ExternalIDEOpenService` handle indexed quick-open, cross-project prompt dispatch, saved script execution, worktree switching, and opening the active worktree in the user's selected external IDE from the top bar. `AskOverlay` reuses the command-palette shell, supports slash commands, file mentions, attachments, task recipes, KajiKit scripts, native Git commands, and inline routing annotations such as `:p:`, `:wt:`, `:t:`, `:m:`, `:h:`, `:s:`, `:task:`, `:pa:`, and `:x:` inside the query field for hands-free targeting. `:git`, `:branch`, `:switch`, and `:checkout` run or select Git operations in the active worktree while streaming output inside the same native command panel instead of opening a terminal tab. `AskCommandDispatcher` routes prompt text into existing terminal sessions when possible and falls back to opening a new provider session before sending. KajiKit scripts are managed by `KajiKitScriptStore`, stored in `~/.kajikit/scripts.json`, resolved by global/project scope, planned into temporary run scripts under `~/.kajikit/runs/`, and streamed inside the command palette by `KajiKitScriptRunner` instead of taking over a workspace pane.
- Guided commits: `:commit` is a native `AskOverlay` flow. Kaji loads the full selected-file inventory, creates an immediate native draft from complete metadata, optionally refines wording through a short-lived Kaji Agent runtime RPC command backed by the same oh-my-pi model catalog and custom providers as the native Kaji Agent pane, and keeps staging plus `git commit` execution inside `GitRepositoryService`. Commit-message settings choose the refinement provider/model from the live Kaji Agent model list, fast/medium/detailed output context, and persisted user wording instructions that are injected into the refinement prompt without overriding the inventory or no-tool constraints.
- Kaji Agent: `KajiAgentHome`, `KajiAgentComposerPanel`, `KajiAgentStore`, `KajiAgentProcess`, `KajiAgentPendingRPC`, `KajiAgentRuntimeReadinessController`, and `KajiAgentRuntimeLocator` provide the native chat surface over the Kaji-owned TypeScript runtime in `KajiAgentRuntime`. The readiness controller resolves runtime readiness off the main actor, `KajiAgentPendingRPC` queues initial RPC frames while it checks Bun and the runtime script, and `KajiAgentProcess` only starts after a concrete launch has been resolved. Source builds run `KajiAgentRuntime/src/kaji-rpc.ts`; packaged builds run the processed `kaji-agent-runtime.mjs` from the SwiftPM resource bundle, including the flattened `Kaji_Kaji.bundle/kaji-agent-runtime.mjs` layout used by release artifacts. Runtime readiness distinguishes missing Bun, unsupported Bun, and missing app-bundle runtime states, caches both positive and negative Bun lookups briefly, and exposes a manual retry from the Kaji Agent header. Runtime error visibility is guarded by `KajiAgentRuntimeErrorGate`. Runtime state is parsed by `KajiAgentRuntimeStateSnapshot`, live turn/tool timeline mutation is centralized in `KajiAgentTimeline`, with assistant and tool-specific runtime events applied by `KajiAgentAssistantTimelineApplier` and `KajiAgentToolTimelineApplier`; `KajiAgentActivityBridge` mirrors native `agent_start`, `agent_end`, transcript, approval, question, abort, and runtime-failure events into the shared `AIActivityStore`, `AgentRunStore`, and `NotificationStore` pipeline so Kaji Agent gets the same sidebar running state, gradient borders, Agent Mission Control rows, unread tab/worktree state, notification sounds, and outbound routes as terminal-backed providers without shell hooks; stable transcript identities are derived by `KajiAgentTranscriptIdentity` for live and restored user, assistant, thinking, tool, and group rows so SwiftUI list identity survives streaming and session restore. Persisted transcript snapshots restore through `KajiAgentTranscriptRestorer`, todo-write progress updates are normalized by `KajiAgentTodoWriteUpdate`, runtime UI requests are normalized by `KajiAgentExtensionRequestParser`, and permission confirms become structured `KajiAgentApprovalRequest` values rendered by the sticky `KajiAgentApprovalBar`. Native host tools are registered through `KajiAgentHostToolCatalog`; file URI reads route through `KajiAgentHostURIResolver` and `KajiAgentWorkspacePathResolver` so workspace boundaries are enforced outside the UI store. Custom model providers are edited from the native Agent settings pane but persisted by the TypeScript runtime through OMP's `~/.omp/agent/models.yml` schema so YAML parsing, validation, model refresh, and discovery behavior stay with the OMP-compatible runtime; Azure OpenAI deployment auto-match uses Azure CLI credentials to list response-capable deployments while model calls still use the configured Azure OpenAI API key.
- Kaji Agent thread rendering coalesces assistant and tool streaming updates before publishing SwiftUI state, keeps session restore from tearing down the scroll surface, and renders transcript rows through virtualized history with stable bottom anchoring. Scroll following is guarded by `KajiAgentScrollLockPolicy`, direction-aware bounds observation, and separate bottom-vs-turn scroll queues so small intentional scroll-away gestures and subagent progress updates are not snapped back during streaming. Tool rows use `KajiAgentToolRenderer` descriptors for command/file-aware labeling and inspector metadata, while `KajiAgentMarkdownRenderCache` reuses parsed Markdown blocks across view refreshes to keep settled transcript rows cheap. Todo and task/subagent activity is summarized by `KajiAgentFloatingTaskState` and shown through a bottom-right `KajiAgentFloatingTaskButton` + `KajiPopover`, while `KajiAgentStore.stop()` locally reconciles in-flight todo/task state so aborting work clears active loaders immediately even if the runtime never emits final task updates.
- Parent Agent: `ParentAgentHome`, `ParentAgentTaskStore`, `ParentAgentController`, and `ParentAgentProcess` form a native SwiftUI orchestration shell over the Kaji-owned TypeScript runtime in `KajiParentAgentRuntime`, which imports Pi through pinned npm packages instead of vendoring the Pi repository. The sidebar's Kaji icon now opens this surface as a global app-level home instead of modeling it as a project or worktree tab, so parent-agent state is independent from workspace tab selection while still operating on the currently active project/worktree context when needed. Kaji launches the bundled or source runtime entrypoint as a child process and exchanges newline-delimited JSON over stdin/stdout; there is no socket server. The controller is split by tool family so workspace tools, child-agent tools, provider choice tools, observation tools, review tools, parsing, and formatting stay separate. Parent tasks persist in `parent-agent-tasks.json`; interrupted in-flight tasks restore as stale, while completed turns leave the parent agent's final answer as the single visible summary. The parent runtime can select projects/worktrees, open terminals/splits, create Git worktrees, spawn provider agents, observe output, stop/resume runs, snapshot changed files, open diffs, and start verification while Kaji remains authoritative for pane IDs, worktree IDs, permissions, and UI state. Before any child-agent spawn, Kaji exposes only enabled and installed coding agents from `CodingAgentRegistry`, renders a native provider/model choice menu, and delegates command/model shape to that agent's definition.
- Browser: `BrowserPaneState`, `BrowserPageState`, `BrowserPane`, `NativeBrowserSurface`, `BrowserWebController`, and the WebKit files under `Kaji/Views/Browser/WebKit/` add an embedded in-Kaji browser split backed by native `WKWebView`. Kaji uses WebKit's persistent `WKWebsiteDataStore` for cookies, login state, localStorage, and sessionStorage; handles navigation, downloads, file uploads, JavaScript dialogs, OAuth popups, screenshots, page text, JavaScript eval, Playwright-compatible ref snapshots/interactions, console capture, WebKit-observed network capture, and WebContent process recovery in Swift/AppKit. `KajiBrowserControlBroker` publishes a session-scoped localhost broker and writes its current session to `~/.kaji/browser/session.json`. The bundled `kaji-browser-mcp` server is installed explicitly from Settings into normal user MCP config files, starts without session-specific shim injection, checks broker reachability through `kaji_browser_accessible`, and always exposes WebKit-native `kaji_browser_*` tools plus Playwright-compatible `browser_*` aliases with structured recovery errors when Kaji Browser is unavailable. Kaji no longer bundles Chromium, CEF, CDP, Playwright, or Chrome DevTools MCP for the embedded browser. Workspace snapshots persist open browser pages and the selected browser page per pane.
- Coding agents: `Kaji/Services/CodingAgents/` is the extension point for terminal-native coding agents. Each agent folder exports a `CodingAgentModule` with identity, aliases, icon, executable names and search paths, config/data directories, default command, install command, prompt/model/resume command builders, skill invocation style, stop automation, model strategy, usage strategy, history strategy, instruction files, skill roots, and hook installation. `AskProvider` is now a registry-backed value type rather than the source of truth, so adding an agent should require adding a module and registering it in `CodingAgentRegistry` instead of editing palette, settings, parent-agent, command, and Mission Control switches.
- KajiCodeGraph: `KajiCodeGraphStore`, `KajiCodeGraphInstaller`, `KajiCodeGraphRuntime`, `KajiCodeGraphVersionArchive`, `KajiCodeGraphInstructions`, `CodingAgentShimInstaller`, `KajiShellBootstrapInstaller`, and `CodingAgentShimEnvironment` manage the optional Graphify-backed code graph extension from Settings. The extension runtime lives under `~/.kaji/extensions/kajicodegraph`, clones a pinned Graphify checkout, creates an isolated Python venv, and runs a Kaji-owned adapter script that emits `graph.json`, `kaji-graph.json`, `GRAPH_REPORT.md`, `analysis.json`, `manifest.json`, and `status.json` per project/worktree. Each graph build captures the current git branch, commit, and dirty state, annotates the latest graph JSON, and archives a versioned copy under the project/worktree `versions/` directory so old graphs can be reopened after newer builds. Kaji renders `kaji-graph.json` in a native SwiftUI graph tab, loads large graph documents off the main actor, exposes latest/commit versions in the graph sidebar, and creates an editable Kaji-owned `AGENTS.md` under the extension project/worktree directory. Kaji terminals prepend `~/.kaji/bin` shims for `codex`, `claude`, `claude-code`, `opencode`, and `pi`, then use a Kaji-only zsh bootstrap to source Ghostty's zsh integration, source the user's real zsh files, and restore the shim directory to the front after shell startup changes. Both footer-launched and manually typed provider commands receive Kaji-only graph context without mutating project or global agent files. The shims preserve provider arguments, add the generated project/worktree graph directory for Claude and Codex, pass Pi its Kaji instruction file through `--append-system-prompt`, and use a Kaji-managed `OPENCODE_CONFIG` file with OpenCode's native `instructions` entry. Browser MCP setup is separate from the shim path: users install the `kaji-browser` MCP server explicitly from Settings, and the server self-checks whether Kaji Browser is reachable before exposing browser actions. Kaji never runs Graphify's instruction-file installers or mutates project agent files.
- Notifications and activity: `NotificationStore`, `NotificationNavigator`, `ProviderEventReceiver`, `ProviderEventDispatcher`, `NotificationIntegrationStore`, `NotificationEndpointSender`, `NotificationRouteSoundResolver`, `NotificationDisplayTextResolver`, `CodexSessionMonitor`, `CodexOutboundNotificationCoordinator`, `AgentProviderCatalog`, `AIActivityStore`, `AIActivitySocketRouter`, `KajiAgentActivityBridge`, `SystemWakeCoordinator`, `ResourceMonitorService`, `ProcessResourceSampler`, `CodingAgentActivityReconciler`, and coding-agent hook installers under `Kaji/Services/CodingAgents/`. Built-in Codex, Claude Code, OpenCode, and Pi integrations emit into Kaji through `KajiHookClient` and `DistributedNotificationCenter`; native Kaji Agent emits directly through `KajiAgentActivityBridge` using its `KajiAgentScope.agentID` as the run identity and explicit parent-agent tab context from `NotificationNavigator`; provider hooks do not install shell notification scripts or interpreter one-liners. `AIActivitySocketRouter` treats only root turn `start` and `stop` activity events as sidebar-running state, carries optional session and turn identifiers to ignore stale stops, and accepts `observe` events for tool, session, subagent, task, and transcript context without lighting the project activity border. `SystemWakeCoordinator` no longer wipes run history on sleep or wake; it restarts Codex/resource monitors and schedules `CodingAgentActivityReconciler` passes that mark interrupted live activities as stale when their pane or provider process does not recover after wake. Codex installs first-party `UserPromptSubmit` and root `Stop` activity hooks in `~/.codex/hooks.json`, observes `SessionStart`, tool, and subagent hooks without starting the border, and gets completion notifications from `CodexSessionMonitor` reading Codex session JSONL files in-process. Claude Code installs `UserPromptSubmit`, `Stop`, `Notification`, and `PermissionRequest` hooks in `~/.claude/settings.json`; OpenCode's plugin uses `session.status` or `tui.command.execute` to start, `session.status` idle/error or `session.idle` to stop, and does not start activity from message, todo, or tool events.
- Agent Mission Control: `AgentMissionControlPanel` is a sidebar footer popover that turns `AgentRunStore` and provider notifications into task-level rows. `AgentRunStore` is the source of truth for provider runs, preserving pane, provider, project, worktree, worktree path, confidence, lifecycle status, changed-file evidence, verification state, recent events, and bounded control-action records in `AgentRuns/index.json` summaries with per-run detail sidecars under `AgentRuns/Details` and changed-file chunks under `AgentRuns/ChangedFiles`; legacy `agent-runs.json` and v1 full-run indexes are migrated and compacted after the v2 summary index is valid; interrupted open runs reload as stale so restart never shows old work as actively running. `AgentRunMissionControlSnapshotBuilder` renders run-backed rows first and keeps provider notifications as fallback rows when no run exists for that pane. Live provider transcript snippets arrive through provider events and stay attached to both the legacy active activity and the new run model in memory. Completed runs capture a bounded git changed-file snapshot only when the worktree is not shared by another active run; overlapping runs in the same worktree are marked `shared worktree` so Kaji does not falsely attribute combined git changes to one agent. `AgentControlCenter` owns row action capabilities and execution for jump, reply, stop, new run, resume, verification, file open, and diff review so the SwiftUI views only render supported controls. `AgentMissionControlRow` keeps changed-file evidence collapsed by default, expands inline to show file paths, statuses, stats, attribution warnings, verification output, per-file open/diff actions, and a compact control tray. Reply and stop require a live exact-pane terminal; stop sends provider-specific Escape key events, with OpenCode receiving two Escapes and other providers receiving one; new run opens a fresh provider tab in the run worktree; resume is shown only when provider session metadata is available. Evidence actions first activate the run's project and worktree so files and diffs open in the right workspace. The initial verification runner detects Swift packages and executes `swift build && swift test` in the run worktree while storing the resulting status and trimmed output on the run. `AgentMissionControlNavigator` jumps from a row back to the owning pane or notification context.
- Settings and theming: `KajiConfig`, `ThemeService`, `AppTypographySettings`, `KeyBindingStore`, `CLILauncherSettings`, `SleepPreventionController`, `CaffeinateSystemSleepAssertionManager`, `PmsetBatteryLidCloseSleepManager`, `HugeIconCatalog`, `HugeIconFont`, and the views under `Kaji/Views/Settings/` and `Kaji/Views/Themes/`. Shared micro controls such as `KajiInput`, `KajiSelect`, `KajiSwitch`, and `KajiButtonStyle` live under `Kaji/Views/Components/` and use only `KajiTheme` tokens so form surfaces do not fall back to native control chrome. `AppearanceModeResolver` resolves the stored solid/translucent/glass preference once into `KajiAppearanceContext`, which is injected from `MainWindow` and consumed by `TranslucentSurface`, `ChromeBackgroundSurface`, and `SidebarBackgroundSurface`; Reduce Transparency forces solid mode, older macOS releases fall back from Liquid Glass to material translucency, and custom Liquid Glass is reserved for top-level chrome, popovers, overlays, and floating panels rather than every micro control. `KajiTheme` derives primary, secondary, tertiary, elevated, and chrome background layers from the active Ghostty theme, so the bundled `Kaji` terminal theme also defines the default SwiftUI hierarchy instead of a flat two-tone shell. `AppTypographySettings` owns the global font family and base font size for both SwiftUI and terminal defaults, and shared `kajiFont` modifiers scale UI text relative to that terminal-driven base. Theme management now supports creating user themes, importing external Ghostty themes, and exporting any discovered theme from the in-app picker. Enabled coding agents are exposed in the active workspace footer, parent-agent choices, notification hook installation, and prompt routing from one `CLILauncherSettings` source.
- Power controls are split by privilege boundary. The regular sleep-prevention toggle uses `ProcessInfo` plus `/usr/bin/caffeinate` for idle and AC system sleep assertions. The advanced battery lid-close toggle asks macOS for administrator authorization through `osascript` and applies `pmset -b disablesleep 1`, then restores `pmset -b disablesleep 0` when disabled or when Kaji terminates cleanly.
- Updates: `UpdateService` integrates Sparkle for macOS app updates.

## Persistence

Kaji stores app data under `~/Library/Application Support/Kaji/`.

- `projects.json`: tracked projects
- `worktrees/*.json`: per-project worktree metadata
- workspace persistence files: tabs, splits, and selection state
- notification persistence files used by `NotificationStore`
- `notification-integrations.json`: outbound notification destinations and routing rules
- `AgentRuns/index.json` plus `AgentRuns/Details/` and `AgentRuns/ChangedFiles/`: recent Agent Mission Control summaries, per-run event/action/verification details, bounded changed-file previews, and chunked changed-file evidence. Legacy `agent-runs.json` and v1 full-run indexes are migration sources and are compacted after a valid v2 summary index exists
- `parent-agent-tasks.json`: Parent Agent threads, timelines, child-run links, and stale restored tasks
- `ghostty.conf`: Kaji-managed Ghostty config snapshot with theme, app-owned terminal typography, terminal behavior settings, optional macOS 26 glass background keys, a default scrollback cap for large-output sessions, and editor-like cursor interaction defaults
- `~/.config/ghostty/themes/*`: imported and user-created Ghostty theme files managed by `ThemeService`
- `cli-launchers.json`: enabled CLI footer launchers and their commands
- `~/.kaji/extensions/kajicodegraph`: managed Graphify checkout, Python venv, adapter script, logs, extension state, latest per-project graph artifacts, and commit-linked graph versions

The source repo may also contain `.kaji/worktree.json` files inside user projects. Those files define setup commands for newly created worktrees.

## Ghostty Integration

`scripts/setup.sh` builds `GhosttyKit.xcframework` from pinned upstream `ghostty-org/ghostty`, then syncs Ghostty's `shell-integration` and compiled `terminfo` runtime resources into `Kaji/Resources/ghostty/` so packaged app builds do not depend on a separate Ghostty.app install for terminal capabilities.

The app only uses Ghostty's public embedding API exposed through `GhosttyKit/ghostty.h`.
